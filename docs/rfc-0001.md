# BitSwarm Protocol RFC 0001 — Selective participation

| Field                | Value                                         |
| -------------------- | --------------------------------------------- |
| Status               | Implemented draft for interoperability review |
| Application protocol | Manifest and signed event version 4           |
| Invitation           | `swarm://` descriptor version 1               |
| Transports           | HTTP and the existing libp2p RPC mapping      |
| Implementing client  | BitSwarm 0.4                                  |

## 1. Purpose

A contributor can inspect a project, choose work, fetch the inputs for that work, and return a verifiable result. The contributor can separately offer storage and upload bandwidth. The project owner defines a goal, a dependency graph, and acceptance rules. An integration task can depend on several accepted component results and apply an end-to-end test to the assembled output.

The capitalized words MUST, SHOULD, and MAY describe conformance requirements in this document. The existing [protocol specification](protocol.md) defines canonical JSON, Ed25519 records, task leases, quorum, recovery, and checkpoint projection. The [URI specification](swarm-uri.md) defines link encoding and bootstrap hints.

## 2. Identity, discovery and preview

The swarm ID is the SHA-256 digest of the canonical genesis manifest. A client MUST verify this digest against the invitation before joining. Peer addresses are discovery hints. Access credentials travel separately. A link can contain a display name chosen by the publisher.

A peer MAY publish a short unauthenticated description by putting a `preview` string of at most 1,000 characters in a v4 manifest. `GET /v1/public-preview` returns only `{swarm,summary}` in this case. Clients MUST treat this advertisement as an unverified statement from the serving peer. Projects that omit the field use ordinary admission for preview. An invited participant receives the manifest and project metadata, including task text, hashes and signed summaries. Publishers SHOULD put private evidence in payloads and choose the preview text and link name accordingly.

An authenticated client fetches `GET /v1/manifest`, validates its digest, and uses `GET /v1/preview` for the peer's current task view. Rows carry the task ID, title, state, prerequisites, capabilities, declared input size, and any configured schema, verifier and token ceiling. Status and size reflect the responding replica. `declaredInputBytes` sums distinct direct input objects and their file chunks. A missing object produces JSON null. Proofs, optional inputs, subsequent results, retries and wire overhead are additional costs. Preview MUST NOT download artifact bodies. Opening a desktop link invokes preview. Explicit join creates a persistent project store.

## 3. Participation settings

| Download mode | Initial and subsequent behavior                                                                                                                                                                        |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `metadata`    | Exchange manifest, inventories and signed events. Request zero artifact bodies. Decline worker claims.                                                                                                 |
| `tasks`       | A fresh contributor starts with zero subscriptions. Selecting or preparing a task adds its inputs and prerequisite result evidence to the wanted set. An explicit list limits scheduling to those IDs. |
| `mirror`      | Request all available and authorized objects, subject to byte limits.                                                                                                                                  |

| Upload mode | Payloads the peer may serve or push                                                          |
| ----------- | -------------------------------------------------------------------------------------------- |
| `results`   | Artifacts referenced by the local identity's signed results and its own verification reports |
| `cache`     | Available cached objects subject to recipient authorization                                  |

A fresh join defaults to `tasks` and `results`. The original seed serves its published inputs. A participant MAY change either direction independently. Choosing metadata stops new payload replication and preserves existing local cache contents. A mirror that chooses results-only still needs other cache-serving peers for input availability.

`downloadBytes` and `uploadBytes` are optional cumulative per-store payload budgets, measured in bytes. The receiver charges accepted artifact bytes. The sender charges before releasing a response or attempting a push. A failed upload attempt may consume budget. The counters persist across restart and encrypted backup/restore. These limits exclude manifest, inventory and event traffic, HTTP overhead and discarded incoming traffic. A zero limit permits metadata exchange. Operators can raise a limit to resume transfer.

## 4. Task inputs and optional context

A block declares `inputs` as an ordered list of content hashes. A file index (`bitswarm.file.v1`) identifies its file name, size, full digest and ordered chunk hashes. Restoration checks the chunk hashes and complete file digest. A file index represents a whole file. Publishers requiring finer scope SHOULD publish separate modules, tables or slices as separate inputs, with offsets or other context in the contract.

Before claiming work, the reference worker subscribes to the chosen block, fetches missing objects and rechecks local availability and lease eligibility. Preparation may require several sync rounds, since a file index or a prerequisite receipt can reveal further hashes. A task-scoped client MUST exclude prerequisite source files unless the chosen task also declares them. It MAY fetch prerequisite result artifacts and verification reports to evaluate acceptance. Current retrieval includes competing candidates in the prerequisite graph. The task workspace contains declared source inputs and granted optional inputs. Its adapter receives accepted direct dependency outputs separately. A verifier receives the candidate artifact and the task's declared source inputs.

Version 4 blocks MAY declare `optionalInputs`. An adapter can request one additional root during an attempt with the following response.

```json
{
  "needInput": {
    "root": "<offered SHA-256 hash>",
    "reason": "Need the palette table to interpret pixel indices"
  },
  "usage": { "tokens": 120, "costMicros": 0 }
}
```

The worker MUST check that the root appears in the block's optional inputs. It signs an `input-request` event with `block`, `root` and a reason of at most 512 characters. The record author identifies the requester. A peer MUST NOT expand its workspace based on another author's request. The worker fetches the optional object, rebuilds the workspace and invokes the adapter with the remaining task budget and original deadline. Both turns count toward the result. The reference worker permits one extra adapter turn per attempt. The CLI can record a request for an offered root before starting work. To add new material outside the offer, the planner can admit a follow-up block with revised inputs.

## 5. Transfer and access enforcement

Both directions use the existing object inventory, wants and GET/PUT routes. Synchronization exchanges signed events and applies the receiver's wanted set for payloads. A serving peer MUST apply its upload policy to blob inventory, direct blob GET and outbound pushes. A receiver MUST enforce its selection and storage budget on incoming blob PUT. Knowing an object digest does not override a serving decision. A capped client can append `?maxBytes=N` to a blob GET. A v4 server returns HTTP 413 before serving an object larger than N. The wants response can include cumulative budget remaining as `remainingBytes`. A results-only mirror pulls its payloads to avoid receiving duplicates through its filtered inventory. Existing transfers resume at verified object boundaries.

For confidential input distribution, a publisher MUST create a v4 genesis with `"restricted":true` and `"policy":{"admission":"invite"}`. Every replica MUST require signed, swarm-bound requests. The owner signs an invitation binding the recipient key, expiry, role, and optionally `blocks` and `roots`. Ordinary contributors can read each granted block's direct and optional input roots, explicit additional roots, and the chunks named by those file indexes. Empty scope grants metadata access. Prerequisite inputs have no implicit grant. A planner can issue another invitation with explicit result and report roots when a downstream contributor needs those objects. The current planner and pinned validators receive full read scope for integration and review.

Restricted swarms MUST disable payload pushes in both directions. A serving node authorizes the identity that pulls the object. This prevents unsolicited delivery to an endpoint whose read grant the sender has not established. The origin or reviewer must have a reachable address for a worker serving its results. Events continue to replicate bidirectionally. An expired or revoked grant fails at a replica that has learned the applicable state. Re-admitting a key requires an invitation issued at or after its most recent revocation on the selected authority chain. Once an authorized recipient obtains plaintext, that recipient can copy it. This mechanism assumes trusted planners, validators, and serving implementations. Use encrypted transport across hosts.

## 6. Running the reference implementation

```sh
bun run swarm preview "$LINK"
bun run swarm join "$LINK" --state .swarm/worker
bun run swarm work --state .swarm/worker --capability palette -- bun examples/codex-adapter.ts
bun run swarm participation --state .swarm/worker --download tasks --upload cache --uploadBytes 8388608
bun run swarm participation --state .swarm/worker
bun run swarm join "$LINK" --state .swarm/archive --download mirror --upload cache
```

Owners can bind files to individual task IDs at initialization. The manifest must already define the task IDs. An optional file requires version 4. For restricted projects, the contributor first generates its own local identity, then sends the public key to the owner.

```sh
bun run swarm init --state .swarm/owner --manifest project.json --taskFile palette=palette.bin --optionalFile palette=table.bin
bun run swarm invite --state .swarm/owner --publicKey "$CONTRIBUTOR_KEY" --only palette --output palette.invite
bun run swarm join "$LINK" --state .swarm/worker --invite palette.invite
bun run swarm request-input --state .swarm/worker --block palette --hash "$TABLE_ROOT" --reason 'Need palette table'
```

Existing version 1–3 projects retain their swarm IDs. Existing stores without a participation profile keep their earlier replication behavior. Newly joined stores use the new defaults even for legacy manifests. Earlier clients reject v4 manifests. The SQLite store migrates to user version 4 and includes participation settings, subscriptions and accounting in new backups. Earlier backups restore with legacy defaults.

## 7. Acceptance and measured pilot

A project SHOULD specify an integrated acceptance test and give the evaluator independent expected results. A signed receipt establishes who reported an outcome. The strength of the conclusion depends on what that evaluator actually checks. A failed integration check should identify an input case that other peers can replay.

The [compatibility pilot](../examples/compatibility/run.ts) compares one Codex worker with three concurrent Codex workers under a shared 90,000-token ceiling per run. Both modes receive the same observations per trial. The three specialties infer image header layout, palette encoding and run encoding. The evaluator supplies unseen component samples and independently encodes 32 complete images per format. The runner assembles validated parameter objects and compares decoded dimensions and RGB pixels against the expected images. The two trials use different formats and reverse run order. The design supplies the component boundaries, candidate parameter space and decoder interpreter. The pilot measures selective participation on this task.

The [recorded results](../artifacts/compatibility/report.json) include elapsed time, time to first verified contribution, payload downloads per worker, token usage including completed retries, unknown usage on failures and integrated checks. Payload counters exclude the metadata exchanged to coordinate each task. Collection, relay and public-network operation need separate measurements for production deployment.
